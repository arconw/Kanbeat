Product and technical design / 28 October 2026

The board drives.
The agents execute.

Arco9 TaskBeat is a local, project-scoped, richly interactive terminal Kanban. Markdown tickets are the source of truth. Native coding CLIs perform the work inside persistent tmux sessions. TaskBeat is a dispatcher and a state validator, not an AI-agent framework.

Self-hosted / local-firstMouse clicks, no hover dependenceMarkdown-firstTextual + tmuxNo agent wrapping

01 / Product contract

01 · Observe

Visualize backlog, queued work, active development, review, done, failures, and sessions in real time.

02 · Dispatch

Pick the top eligible Todo ticket, run the selected native CLI, and let its ticket status change trigger the next stage.

03 · Resume

Remember tmux targets, native CLI session references when known, ticket bindings, and custom sessions.

Non-goal: inventing an agent protocol, replacing the existing harness UI, changing permission/sandbox flags, storing model transcript dumps inside ticket Markdown, or running different tickets concurrently.

02 / Hard invariants

  • Project root = directory where the command is started, unless an explicit path is passed. Tickets live in .tasks/*.md; archive lives in .tasks/archive/*.md.
  • Zero or one active ticket globally per project. Multiple reviewer sessions may run in parallel only for that same ticket.
  • Backlog is never auto-picked. Todo is processed by ascending order, then stable ID. Archive entries are not scheduled.
  • Every existing harness is invoked through its own executable, using user-configured command and inherited environment, sandbox, authentication, permission settings and working directory.
  • Only a legitimate state transition causes dispatch. Never infer completion from terminal output. Agent-written Markdown state or the bundled CLI state command is authoritative.
  • Closing FMODAL detaches the view. It does not stop a session. Explicit Stop requires confirmation; ticket-owned sessions cannot be stopped from ticket UI.
  • Logs remain outside the ticket. Past transcript context is only injected on harness change, reset, or a verified session handoff, never consumed by other agents automatically.
  • Maximum 3 launch / recovery attempts per worker, then mark the ticket Failed and notify. Notify when the eligible queue drains.

03 / Visual language

Dense but calm dark TUI, sharp information hierarchy, cold charcoal surfaces, subtle cyan/purple highlights, compact action pills, clean typography, no decorative ASCII borders around full-screen modals. Color is supplementary to text. Responsive behavior must work down to a documented minimum terminal size (target 100x30, graceful compact fallback below it).

FMODAL

Edge-to-edge workspace

Full terminal viewport, zero outer margin, zero border. Top-right Close. Optional Cancel/Save footer. Body: native tmux terminal, log viewer, or multiline editor. Restores focus on close.

SMODAL

Compact dialog

Centered inset modal, content-driven width/height with min/max. Close button, form fields, dropdowns, destructive confirmation and short editor.

Popup / Dropdown

Anchored options

Click to open menu anchored to control, auto-flip near edges, keyboard navigation, Escape dismissal and click-away. No hover requirement.

Mouse: cards, tabs, buttons, selectors, checkbox selection, scroll, list actions. Keyboard parity: Tab, Shift+Tab, Enter, Escape, arrows, quick shortcuts; accessible focus states.

Developer may author tests but does not execute tests. Reviewers test; prefer headless tools when suitable. 0..N reviewer instances, concurrent for one ticket. Each instance gets a unique worker ID and independent harness/session configuration. All reviewers receive peer roster and common iteration ID in their initial instructions.

06 / Sessions · Tab 2

Orca-inspired tree. Default Tasks group is collapsed and lists board tickets, each expandable to its developer and reviewer sessions. User-defined groups persist across launches, with named custom native CLI sessions and attach targets.

  • Click a session to open FMODAL containing the live tmux-backed terminal. Interactive keyboard input stays native. Close means detach, never kill.
  • Explicit Stop exists on Sessions tab with a confirmation SMODAL. Ticket-owned sessions remain protected from Stop as long as the ticket is in scope.
  • Store session registry in .tasks/.state/sessions.json; discover tmux target after restart, perform native CLI resume when needed and supported. If a live tmux session still exists, reattach instead of relaunching.
  • Native CLI session IDs are optional adapter metadata and are never invented. If resume support is unavailable, report it and request an explicit fresh start.

07 / Archive · Tab 3

Searchable, sortable list of archived tickets (title, last status, archive date, prior owner). Row actions: Restore to Backlog / Todo, view FMODAL, Delete with confirmation. Bulk restore and bulk delete. Archive operation physically moves the Markdown file into .tasks/archive and removes it from dispatch scope; archive is not merely a visual filter.

08 / Settings · Tab 4

Defaults

Default harness, Global CP, Developer prompt, Reviewer prompt; default shell command templates for Codex CLI, Claude Code CLI, OpenCode CLI, Pi CLI. Preserve native configuration.

Transition hook

Separate harness + prompt executed between ticket transitions for optional GitHub issue synchronization and other user automations. Hooks must not break state safety. Failure is reported separately.

Default reviewer prompt: review code and verify with tests; prefer headless. Default developer prompt: implement and optionally write tests, but do not run tests. All agent prompts state the allowed status transitions and show the built-in task CLI commands.

09 / Lifecycle & coordination

Backlog→ manual →Todo→ worker starts →Progress→ developer →Review→ consensus →Done
Review→ changes requested →Progress→ next iteration →Review
Any active→ 3 failed attempts →Failed→ manual recovery →Todo / Backlog

Developer attempt to jump progress → done is normalized to review; the worker receives a short correction. With zero reviewers, a review-stage pass can automatically reach Done. Reviewer outcomes must be independent and identified by reviewer ID. A reviewer cannot overwrite the main status before peers finish.

Iteration 7: pending [r1, r2, r3]
r1 → approve    r2 → changes_requested    r3 → approve
All 3 reported → remove review_iteration → Progress
If all approve → remove review_iteration → Done

Agent-facing interface: taskbeat status <ticket> review for developers and taskbeat review <ticket> <reviewer-id> approve|changes_requested for reviewers. This is a safer equivalent to editing frontmatter directly and handles concurrent updates with a project lock. Direct edits are watched and validated, but simultaneous external writes may still race unless the CLI is used.

Tick ordering: observe filesystem → validate/normalize transitions → reconcile current worker → dispatch relevant role → release ticket only on Done/Backlog/Archive/Failed. Never start another Todo ticket while any active ticket exists, even if that ticket currently has no live worker.

## Goal
Refactor the database layer without changing the public API.

Use YAML frontmatter + Markdown body. Unknown frontmatter fields are preserved on updates. Minimal metadata only: IDs, order, status, role configurations, native session IDs when known, iteration coordination. No transcript logs, token usage dumps or raw tool results in tickets. Archive metadata can store prior status. Files are written with atomic replace under a project lock.

Changing a session/harness may retrieve a bounded transcript from tmux capture history or the native CLI resume source if exposed. Mark handoffs as untrusted prior output. This is a conscious exception to the default "no agents read logs" rule, invoked only for a verified session change/reset.

11 / Native harness contract

OpenCode CLIopencodeNative interactive process in tmux, no permission flags
Pi CLIpiNative interactive process in tmux, no permission flags

Adapters provide command selection, tmux lifecycle, input and optional verified native session resume. Never simulate an agent runtime inside TaskBeat. Real CLI interactivity requires a PTY-backed terminal widget. The proposed Textual integration is textual-tty behind an optional adapter, with isolated compatibility testing required before claiming parity with the host terminal. Fallback: detached tmux session plus capture-pane and explicit text input, without pretending this is a full terminal.

When a stage changes, do not automatically paste logs into the next agent's context. Pass only ticket description, current state, role prompt, user CP and coordination instructions. Prior logs may be handed over only if changing harness/session or resetting, with size limits and user-visible provenance.

12 / Stack and architecture

Presentation

Python · Textual

CSS-like TCSS, reactive widgets, mouse clicks, TextArea, Select, modal screens, data-driven Kanban. Rich for styled text.

Sessions

tmux + optional PTY

Native processes, retained tmux sessions, capture-pane, send-keys, lifecycle isolation. External tmux binary required.

Persistence

Markdown + JSON

PyYAML frontmatter, atomic writes and file lock. Polling initially; inotify/watchdog optional later.

Dispatcher

Deterministic event loop

File status transitions, validation, sequential ticket queue, worker retry policy and notifications. No LLM in orchestration layer.

Textual UI ──→ TicketStore (atomic Markdown)
       │               ↑
       │               │ external edits / agent CLI
       └──→ Dispatcher ─┴──→ HarnessManager ──→ tmux ──→ native CLI
                 │                  │
                 └──→ Notifications └──→ Session registry

Safety boundary: do not use shell interpolation for ticket titles/prompts. CLI executable is taken only from explicit user configuration. Prompt text is passed as terminal input via a temporary private tmux buffer and removed. Preserve parent process environment. Do not silently enable dangerous permission flags.

14 / Open engineering decisions

PTY terminal fidelity

Terminal-in-terminal programs may depend on private ANSI sequences, clipboard integration, focus, mouse tracking and resize. Treat textual-tty as an optional experimental dependency until manually proven with all four CLIs. Session lifetime must not depend on it.

What exactly counts as native resume?

tmux reattach is unambiguous. Native CLI resume is version-specific and must never assume a resume flag or fabricated session ID. Store observed IDs only and introduce per-harness verified adapters with capability detection.

Retry and hung detection

Missing tmux process and launch errors can be retried 3 times. A responsive but idle model must not be declared hung from elapsed time alone. Offer explicit configurable inactivity timeout with warnings rather than terminating without consent.

Transition hooks

Fire hooks once per transition with an idempotency key and isolated session. A failed external sync must not roll back a legitimate ticket state. Build durable hook ledger before declaring hooks production-ready.

Handoffs across agents

Only switching/resetting sessions permits log handoff. Trim and label previous agent output, avoid claiming old transcripts are safe instructions, and do not record sensitive output into Markdown tickets.
