Kanban that
runs itself.

Kanbeat is an advanced terminal UI backed by one persistent project supervisor. Tickets are simple Markdown documents, statuses are directories, and native coding CLIs execute the pipeline without being reimplemented as agents.

01 / Non-negotiable product contract

Filesystem is the board

Every ticket is a .md with title and description. The folder determines status. First filename number determines order; second determines permanent ID.

Supervisor is persistent

One daemon per project owns dispatch and state. Clients attach over a private Unix socket and may close independently without stopping work.

CLIs are native

Codex, Claude Code, OpenCode and Pi keep their own sandbox, permissions, model settings and session history. Kanbeat only starts, stops and observes them.

Out of scope: diff ownership, Git worktrees, auto commits, Git cleanup/reset, orchestration frameworks, automatic transcript exchange between roles, editing task body from the UI, safeguarding deliberate deletion of live runtime files.

## Acceptance criteria
- Validate tokens.
- Reject expired credentials.

Tickets contain no YAML frontmatter or hidden control fields. Moving a file changes the status. Renaming the first segment changes its order. Sorting compares it numerically: 2 comes before 10. ID is unique across every board column and archive, and does not change with moves. Slug remains descriptive.

An external agent may create or edit tickets only when the user separately asks it to and points it to .kanbeat/INSTRUCTIONS.md. The guide is not an implicit system prompt.

If .state is absent, all ticket files retain their column statuses and the board starts in Stopped mode. Missing assignments resolve to the configured default harness when Play is pressed. Active deletion of the runtime directory is intentionally unsupported.

A detached supervisor continues when every TUI window is closed. A second kanbeat in the same project connects to the existing supervisor instead of starting another dispatcher. Starting Kanbeat in another project creates an independent supervisor. Separate supervisors do not isolate shared Git working trees; nested project setups may share files by choice.

Use a single-writer lock for supervisor ownership and atomic writes for private JSON. Persist native session IDs when the CLI exposes them. Running tasks also carry starting, running, interrupted, recovering, completed and failed runtime states. None are stored inside Markdown.

06 / Board Play / Stop semantics

Stopped▶ Play →Running■ Stop →Stopped
  • Stop: disable dispatch first; interrupt every current board-owned native CLI turn; gracefully exit those processes, persisting native IDs when known. After timeout, terminate process groups. Do not change ticket status or increment retry count.
  • Play: attempt native resume of unfinished slots using saved IDs, with a short continuation instruction. If session is confirmed missing, begin fresh in the same slot. If a specific assigned harness is unavailable, fall back to default with fresh context. If default is unavailable, global Stop and wait for user to configure it and press Play again.
  • Close TUI: detach UI only. Custom Sessions: not controlled by the board Stop.

Native resume restores conversation context, not suspended CPU execution or partially executed shell tools. Continuing workers must inspect the current repository and avoid repeating completed side effects.

07 / Execution lifecycle

Backlog→Todo→Progress→Review/QA→Done

Backlog is inert. Todo is processed top-to-bottom by order and ID. There can be only one active ticket at a time, but within Review/QA multiple reviewer workers run in parallel. Agents are given the current file path of the ticket, not a pasted copy of its Markdown. They must read that Markdown from disk and never edit, rename or move the ticket, nor write Kanbeat status or runtime metadata. Native structured turn completion triggers advancement only after confirming that the worker handled the current ticket content. A failed or interrupted turn is not a completed turn.

Developer may write tests but does not execute them. Reviewers run relevant tests and prefer headless solutions. Review verdict is a structured final-line contract: KANBEAT_VERDICT: approve or KANBEAT_VERDICT: changes_requested. The marker is emitted by the reviewer as the final line of its response.

Live ticket edits · same-session re-read

Ticket Markdown is user-editable outside Kanbeat, including while a worker is running. The supervisor records a SHA-256 content hash for each worker turn in .kanbeat/.state/. It does not rely on mtime, path or Git diff. A user editing the ticket does not interrupt or restart active harnesses.

When a turn ends, before applying its completion or review verdict, the supervisor resolves the ticket's current path from its stable ID and compares its current content hash with the version that worker received. If changed, the ticket stays in its current stage and the same native session gets an instruction to re-read the current file, account for new requirements and continue. No full Markdown is re-injected into the prompt.

Read .kanbeat/progress/0-002-authentication.md and work on this task.
This Markdown is read-only to you. Never edit, rename or move it.

# Later, after content changes and the current turn completes:
Ticket #002 has changed. Re-read <current-ticket-path>,
reconcile the updated requirements with existing work, and continue.
Do not modify the ticket.

Changing just the order prefix, slug or location does not count as a content edit; dynamically resolved paths prevent stale references. During Review/QA, verdicts tied to a superseded content hash cannot approve the revised ticket. Each affected Reviewer slot must produce an updated verdict for the current hash, still without receiving Developer or peer Reviewer transcripts.

Implementation status: initial hash-and-re-read lifecycle implemented in supervisor. Compatibility and end-to-end execution remain unverified.

At normal stage completion, supervisor moves the ticket file. When Reviewers disagree, a short review feedback summary may be given to Developer during the next iteration, but never the full Reviewer transcript. No special worktree handling or Git diff calculation.

Custom between-stage hook: a configurable harness and prompt may run after ticket transitions, for optional GitHub issue closing and other automations. Hook failure is separate from ticket success and does not automatically revert ticket state. The supervisor queues hooks for its own column changes, runs them serially on Play before further board work, and starts a fresh native session for each event. A local ledger prevents automatic replay of settled or interrupted hooks; Stop also interrupts hook processes. File moves and ledger writes are not one atomic transaction, and external side effects are not guaranteed exactly once. See README for recovery limitations.

08 / Reviewer isolation and slot replacement

Fresh reviewer context

Each Reviewer receives the path to the current canonical ticket, applicable global/reviewer/slot CP and minimal workflow instructions. It independently reads the task from that Markdown, which it must not edit, rename or move, and examines the working tree. It receives no Developer transcript, logs, developer-specific CP or generated handoff summary. User edits to the ticket are picked up by the same-slot hash-and-re-read workflow, never by cross-role log handoff.

Reviewer 1 · Claude

Can later be replaced by Codex inside reviewer-1, using reviewer-1's bounded prior output if available.

Reviewer 2 · Pi

Independent. Never sees reviewer-1's logs, even when both run concurrently.

After every slot delivers a verdict, all approve → Done, any changes requested → Progress. Completed slots never restart just because another is still working. Native session resume stays tied to the exact same ticket, role and slot ID. A new slot begins without any previous reviewer history.

09 / Sessions · Tab 2

Target UX is an Orca-inspired tree: Tasks group collapsed by default, tickets expandable into Developer and Reviewer slots; custom user-defined groups with standalone sessions. Opening a native harness uses borderless FMODAL. Closing FMODAL never kills a process. Independent custom sessions require explicit Stop confirmation. Deleting the active ticket from dispatch scope removes only its board assignment, not arbitrary other user sessions.

Current implementation boundary: supervisor-owned interactive PTYs are implemented for task slots (#2). They open while structured dispatch is stopped; detach preserves the process, explicit Stop terminates it, and Play prevents simultaneous native session use. Custom user-defined session groups remain tracked in #3. See terminal documentation for recovery and vendor-session limits.

10 / Settings · Tab 4

Default Harness; Global CP; Developer prompt; Reviewer prompt; between-transition hook Harness and Prompt; UI theme/presentation later. Configuration persists in .kanbeat/config.json, outside disposable .state. Ticket-local harness, CP, session identity and Reviewer slot roster live in .state, never in ticket Markdown.

Kanbeat deliberately favors a small, deterministic dispatcher over a general multi-agent platform. A ticket is a document. A status is a directory. A worker is a native CLI. The supervisor coordinates the handoffs. The user controls Play and Stop.
